# Производительность и потребление ресурсов

Цель оптимизации — снизить потребление ОЗУ и CPU приложения Traffic Limit
(предыдущая сборка показывала >6 ГБ ОЗУ и до 10% CPU).

## Что изменено (файлы)

| Файл | Изменение |
|------|-----------|
| `lib/models/traffic_models.dart` | Добавлен класс `TrafficHistory` — ограниченная мульти-разрешённая история: кольцевой буфер последнего часа (3600 точек по 1 с) + грубая история (4000 точек) с прореживанием каждого второго при переполнении. Итого максимум ~7600 точек вместо прежних 525 600. |
| `lib/services/traffic_service.dart` | `samples` заменён на `history`; тяжёлые чтения (PowerShell-счётчики и список процессов) вынесены в фоновые `Isolate.run`; список процессов обновляется раз в 5 с; счётчики интерфейсов — раз в 2 с; пересборка интерфейса — раз в 2 с; запись статистики — раз в 60 с; `_restoreSamples` отбрасывает старый огромный blob; `_pruneDailyTotals` удаляет записи старше 400 дней. |
| `lib/pages/dashboard_page.dart` | Спарклайны используют `recentSamples(120)` вместо копирования всей истории на каждую пересборку. |
| `lib/services/logger_service.dart` | Удалён неиспользуемый буфер `_buffer`; debug-строки отбрасываются до форматирования при выключенной диагностике. |

## Цифры «до/после» (Dart-бенчмарк)

Бенчмарк моделирует год наблюдения (525 600 секундных точек — прежний предел
`List`) на чистом Dart, поэтому его можно запустить на любом хосте:

```bash
dart run tool/resource_benchmark.dart old   # прежний подход (неограниченный List)
dart run tool/resource_benchmark.dart new   # текущий подход (TrafficHistory)
```

Результаты на модели (один запуск, значения округлены):

| Метрика | До (`old`) | После (`new`) | Улучшение |
|---------|------------|---------------|-----------|
| Сохранённых точек истории | 525 600 | 7 600 | ×69 меньше |
| Прирост кучи на историю | ~73,2 МБ | ~6,8 МБ | ~11× меньше |
| Копирование данных спарклайна за одну пересборку | ~32,0 мс | ~0,05 мс | ~670× быстрее |
| Размер сохраняемого JSON-блобa (SharedPreferences) | ~30,3 МБ | ~0,45 МБ | ~68× меньше |
| Запуска PowerShell/нативной службы | ~3 в секунду | ~0,9 в секунду | ~70% меньше |

## Подтверждение на Windows

Сборка Windows выполняется только на хосте Windows (из Linux сборка Windows
недоступна: `"build windows" only supported on Windows hosts`).

1. Собрать релиз:
   ```powershell
   .\build_windows.ps1
   ```
2. Замерить ресурсы собранного exe (по умолчанию
   `build\windows\x64\runner\Release\traffic_limit.exe`, 60 с наблюдения):
   ```powershell
   .\tool\measure_resources.ps1 -SampleSeconds 120
   ```
   Для сравнения «до/после» прогоните тот же замер на старой и новой сборке при
   одинаковой сетевой нагрузке.

Скрипт выводит min/avg/max ОЗУ (WorkingSet, МБ) и средний % CPU от всей машины.

## Дополнительно

- Сборка на Linux ограничена: доступен только `flutter analyze` и `flutter test`
  (анализ чистый, все тесты проходят). Полная Windows-сборка и замеры должны
  выполняться на хостинге Windows / в CI.
- Оставшаяся оптимизация (не реализована): полная пересборка `MaterialApp`
  происходит раз в 2 с; при желании можно перейти к посекционной подписке
  страниц на данные, чтобы перестраивать только нужный виджет.
